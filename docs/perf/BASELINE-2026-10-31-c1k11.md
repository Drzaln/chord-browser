# c1k.11 — hidden pages, 2026-10-31 (early morning)

Release build, the tab set in Spaces 3 and 4, both YouTube videos confirmed
paused in WebKit's log (`pauseInternal`), Chord hidden (Cmd-H). Per-process
CPU from `ps` cputime over 120 s, after settling (3 min before, 5 min after).

| | before | after `hiddenPageDOMTimerThrottlingAutoIncreases` |
|---|---:|---:|
| YouTube page processes | 16.3 + 9.8 ms/s | 9.2 ms/s |
| All Chord processes | ≈48 ms/s | ≈26 ms/s |

Safari turns this WebKit preference on: a page's timers are spread further
apart the longer it stays hidden. WebKit leaves it off for apps. The
comparison is not perfectly controlled (a relaunch in between; the second
YouTube tab may share the first one's process after it), so the next
powermetrics run of the tab set is the real number.

Also found on the way: a playing video costs the GPU process ~43 ms/s
hidden (a live CoreAudio output loop plus sample enqueueing), and the
tab-set script's YouTube tab autoplays, so a "paused" run has to check the
log, not the screen.

## What the paused YouTube tabs cost, and why Safari pays nothing (06:00–06:45)

Same protocol per build (relaunch, load both Spaces, pause both videos and
check `pauseInternal` in WebKit's log, hide, 5 min settle, `ps` cputime over
120 s). YouTube processes found from their MediaSource log lines.

| Build | YouTube processes (ms/s) | All Chord |
|---|---|---:|
| A: HEAD (87adcce) | 11.0 + 12.1 | 45.5 |
| B: no YouTubeAdBlocker script | 12.6 + 11.1 | 50.6 |
| C: no extensions loaded | 14.8 + 8.0 | 54.8 |
| Safari, same two videos, paused, hidden | 0 + 0 | — |

Neither Chord's YouTube script nor Bitwarden/uBlock is the cost: it is
YouTube's own JavaScript, ~11 ms/s per paused tab. Safari pays nothing
because it **suspends** the hidden page's process a few minutes after it is
hidden (`didChangeThrottleState(Suspended)` at 06:40:41, hidden ~06:37).
Chord sets `inactiveSchedulingPolicy = .throttle` for tabs on purpose
(background music, chat sockets), so a hidden page's scripts never stop.
WebKit keeps a page that is playing audio running whatever the policy, so
`.suspend` would cost the music case nothing; the open question is pages
that should keep working unseen (chat sockets, web notifications).

The hidden-timer auto-increase (87adcce) is worth little over 5 minutes:
A's 23 ms/s for both tabs against ~26 before.

## "Suspend tabs you can't see" (Settings > General, on by default)

Same protocol, Release build with the toggle on (WebKit's
`inactiveSchedulingPolicy = .suspend`; off = `.throttle`, the old way).

| | YouTube processes | Chord's processes |
|---|---|---:|
| Throttled (A above) | 11.0 + 12.1 ms/s | ≈45 ms/s |
| Suspended, first minutes | 6.3 + 2.8 ms/s | ≈30 ms/s |
| Suspended, steady (worker held) | ≈0 | ≈10 ms/s |

The first minutes aren't zero because Bitwarden, signed out, restarts its
worker every minute until c1k.9's hold takes it, and each start calls into
every tab (`scripting.executeScript`, one Code=7 error per tab), which makes
WebKit ask each page for its frames (`WebFrame_GetFrameInfo`) and wakes every
suspended process. Once the worker is held the wakes stop. (`cpu.sh` totals
also counted Safari's WebKit processes while it was open; the steady figure
above leaves them out.)
